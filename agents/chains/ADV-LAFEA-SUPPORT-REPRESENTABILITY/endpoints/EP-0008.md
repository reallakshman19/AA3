## Newly isolated integration defect

The HANGER backend correctly creates H-bearing cases with roles:

- `WEIGHT_HANGER_PRELOAD`
- `WEIGHT_PRESSURE_HANGER_PRELOAD`
- `WEIGHT_TEMPERATURE_HANGER_PRELOAD`
- `WEIGHT_PRESSURE_TEMPERATURE_HANGER_PRELOAD`

and `buildInputXmlRunRequestCase()` can execute any compiled physical case by `caseId`.

However, live `src/workspace/lfea-pipeline-case-selection-panel.js` only classifies the four non-H roles as `STANDARD`. H-bearing roles fall through to `OTHER`. When no explicit checkbox selection exists, `getSelectedCaseIds()` defaults only rows with `category === 'STANDARD'`. A model containing a qualified predefined HANGER can therefore default to `W/WP/WT/WPT` and silently omit the theoretical cold-load primitive even though H-bearing cases exist.

This is case-selection custody, not a defect in spring-rate, cold-load, multiplicity or solver mechanics.

## Safe material patch

1. Add explicit presentation mappings for the four H-bearing roles.
2. Classify them separately as hanger-standard cases.
3. If hanger-standard cases exist and there is no explicit user selection, default to the H-bearing set only.
4. If no hanger-standard cases exist, preserve the existing legacy default exactly.
5. Keep base `W/WP/WT/WPT` rows visible and explicitly selectable for comparison.
6. Preserve explicit user selection as authoritative.
7. Add a focused deterministic check and register it in `lfea-spring-draft-model-check.mjs`.

No H load is derived in the UI. The UI consumes case roles already created by the governed physical-case compiler.
