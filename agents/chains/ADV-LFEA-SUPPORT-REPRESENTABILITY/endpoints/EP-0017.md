## Material change

A bounded production-path audit was performed because exact-head execution and external CAESAR support references remain unavailable.

The audit traced solver execution through normal orchestration, B-3.4 recovery, retained-result composition and the public linear-piping result relationship validator. `runLinearPipingAnalysis()` and B-3.4 recovery already failed closed on `execution.status === BLOCKED`. The retained-result composition boundary, however, relied on those downstream guards rather than refusing a blocked B-3.3 execution explicitly at its own public composition boundary.

The following defense-in-depth hardening landed without changing stiffness, loads, solver tolerances, result values or UI behavior:

- `retained-result-chain.js` now explicitly refuses a blocked execution with `PIPING_ANALYSIS_EXECUTION_BLOCKED` before composing a public result;
- `contracts.js::requireResultRelationships()` independently refuses a blocked execution with the same application-level code;
- `scripts/lfea-blocked-execution-custody-check.mjs` verifies the four fail-closed boundaries and contains a deliberate-break mode for the retained-composition guard;
- the new check is imported by `lfea-spring-draft-model-check.mjs`, so it participates in the support aggregate rather than existing as orphan coverage.

Important classification correction: the pre-hardening code did **not** provide a valid path to publish a BLOCKED solver execution as a qualified result, because B-3.4 recovery already refused BLOCKED and the recovery contract accepts only QUALIFIED/CONDITIONAL execution status. This endpoint records the change as earlier deterministic custody hardening, not as a previously exploitable numerical bypass.

## Mixed fixed + directional spring reaction audit

The same trace identified a separate bounded risk that is not being patched speculatively.

Directional ground springs publish component reactions in UX/UY/UZ, while fixed constraints publish residual reactions. The solver execution contract validates each reaction row but does not require unique `nodeId:dof` identities. A valid model can place a directional spring at a node that also has one or more translational FIXED restraints, because directional springs intentionally do not occupy one scalar DOF slot.

The existing `SkewSpringSupports.xml` fixture does not exercise that mixed case: the anchor is at node 10 and the directional spring is at node 40. Therefore no evidence yet proves whether the public reaction contract should aggregate same-node/same-DOF support contributions or retain an explicit decomposition. `generic-inputxml-solve-case.js::nodalResult()` currently uses `.find()` and would be order-sensitive if duplicate reaction rows occur.

No reaction representation has been changed from source reasoning alone. The next bounded engineering action is to author a mixed fixed + directional ground-spring exercise and use it to resolve the public reaction-row invariant before promotion.
